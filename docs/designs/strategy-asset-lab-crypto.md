## Problem Statement
AlgoSystem trades one strategy on one symbol live (AAPL 5/20 SMA, 2x leverage, once per trading day via `.github/workflows/run_daily.yml`, triggered by cron-job.org; `run_daily.yml`, `intraday_check.yml` and `eod_summary.yml` all commit state back to `main`). Research strategies under `tests/` each define their own signal code and cannot be swapped onto other assets. The goal: "a lab that lets me swap assets and strategies and see the results", that can also trade live, since "the end goal is to make money off of this". First new asset class: crypto, which is 24/7 and which the user wants tracked and tradable "at the very quickest, every 5 minutes".

Current limits found in the code:
- Live path hardwired: `run_daily.py` imports `aapl_sma`; risk code takes one `symbol`.
- Risk state is global: single `halt_state.json` / `daily_loss_state.json`; drawdown reads whole-account equity.
- Stocks only: `int` share counts, `TimeInForce.DAY`, market-open gate, stock-only data calls in `market_data.py` (`StockHistoricalDataClient`, `StockBarsRequest`).
- The lab harness is daily/stock-only: `portfolio.load_ohlcv` hardcodes `interval="1d"`, `portfolio.summary` annualizes with 252, `BAR_CONFIG` uses stock-session bars per year.
- Always-on crypto cannot run on the current cron + ephemeral-runner + commit-state model.

## What Makes This Cool
Drop in any asset (AAPL, SPY, BTC, ETH; stocks and crypto each in their own set for now) and any strategy, get a fees-adjusted result in one command, and later promote the winner to live with a config change instead of a rewrite.

## Constraints
- `claude.md`: keep it simple; the goal is to teach how this works and how to reach production-level code, not to be production-ready.
- Real money is the end goal, so live-path changes need tests and a promotion gate.
- IBIT overnight (open/close gap) does not translate to 24/7 crypto; stays stock-only.

## Scope split: what Approach A builds vs what waits for B
Approach A is lab only. These files stay byte-identical, because the live scripts import them directly or transitively: `src/strategy/aapl_sma.py`, `src/trading/*`, `src/risk/*`, `src/data/market_data.py`, `src/config.py`, `src/bar_config.py`. All new code goes in new modules: `src/data/crypto_data.py` (crypto loader and its `BAR_CONFIG_CRYPTO`) and a new lab area for the strategy contract and CLI. `src/backtest/portfolio.py` is edited, but only research scripts import it. Anything that places an order or changes risk state is B.

## Premises
Each is tagged with the approach that delivers it.
1. [A, B] One repo. Lab and live stay together; separation is by credentials and a GitHub Environment gate. Revisit if taking investor money. (Clone/branch rejected: the bot commits state to `main` from three workflows, so branches would conflict and drift.)
2. [A] Strategy contract: every strategy is one function. Exact shape, so the same code serves backtest and live:
   `strategy_fn(ohlcv: dict[str, pd.DataFrame], **params) -> pd.DataFrame` where `ohlcv` maps symbol to an OHLCV frame (oldest first, the shape `load_ohlcv` already returns; close-only strategies call `closes(ohlcv)`) and the result is a weights table indexed by date with one column per symbol. Row `t` is the target weight per symbol decided at bar `t`'s close, as `portfolio_returns` already assumes. Rows may sum to more than 1 to express leverage (2x = a row summing to 2.0); `portfolio_returns` already charges slippage on weight turnover. Live later takes `weights.iloc[-1]`. [Eng review D1]
   Single-symbol signal strategies wrap to this shape: weight = `signal * TARGET_ALLOCATION_PCT * LEVERAGE_MULTIPLIER`. `dual_momentum_weights(close, lookback)` already matches the shape. In the lab, crypto runs at 1x (no leverage).
   Calendar rule for A: a backtest mixes only assets that share a calendar (stocks with stocks, crypto with crypto), because `load_ohlcv` trims to the dates every symbol has and an AAPL + BTC mix would silently drop every BTC weekend. `periods_per_year` comes from the asset class (252 stock, 365 crypto). Mixing across classes needs an explicit alignment rule and is B.
3. [B] Asset adapter: stocks and crypto behind one adapter (data source, fractional qty, time-in-force, trading hours). Strategies never know the asset class. A only needs the data half (premise 5's loader).
4. [B] Per-strategy risk: halt, daily-loss and drawdown state namespaced per strategy, global account kill switch above.
5. [A] Crypto is 24/7 and 5-minute-capable (user revision). The bar interval is a parameter, not a constant, and annualization comes from the interval (365-day basis for crypto).
6. [B] Promotion gate: walk-forward MCPT plus a paper-trading period before any live money. Thresholds (p-value, paper-period length) are deferred to B's design; A only produces the evidence.
7. [A decides, B builds] (Revised after second opinion) An always-on crypto runner is built only if the fees-adjusted backtest rule in Success Criteria says finer bars pay. The user chose this over building the runner up front.

## Success Criteria
1. One command backtests any strategy on any set of same-calendar symbols (e.g. AAPL + SPY, or BTC + ETH) through the same `strategy_fn` and prints the same summary table (`total %`, `cagr %`, `sharpe`, `maxDD %`). The same SMA `strategy_fn` runs on an equity set and a crypto set. No order is placed in A. Also: `--grid` runs every registered strategy that is compatible with the symbol set and prints one comparison table, skipping incompatible strategies with a stated reason (CEO X1); every run appends one row per strategy to `data/backtest_results/lab_runs.csv` (CEO X2).
2. The SMA strategy is ported as a new wrapper file in the lab area, and `git diff` shows no change under `src/strategy/aapl_sma.py`, `src/trading/`, `src/risk/`, `src/data/market_data.py`, `src/config.py`, `src/bar_config.py`.
3. Unit tests (pytest, `tests/unit`) cover: golden-master equality of today's `load_ohlcv` default, `portfolio_returns` (rows <= 1) and `summary(r)` on a fixed synthetic dataset, captured before editing `portfolio.py` (D3); `portfolio_returns` with leverage; `summary` with 365 vs 252 `periods_per_year`; `execution_delay_bars=1` shifts weights and cost one bar; shifted-return alignment on a non-daily grid; SMA wrapper parity with `aapl_sma.compute_signal` on the last bar and zero weights during warm-up; crypto loader raises on empty data, fills a dropped bar and reports the count; the CLI refuses mixed asset classes, symbol/asset-class mismatches and intraday stock intervals (D8); the `STRATEGIES` registry lists each strategy's requirements; `--grid` prints one row per compatible strategy and skips an incompatible one with a reason (X1); the results log appends exactly one row per registry entry per run, writes its header once and refuses a file whose `schema_version` differs (X2); the loader re-raises an Alpaca `APIError` with symbol, interval and range, and raises when the request starts before the data (X4); a results-log write failure warns without losing the printed result; `periods_per_year(asset_class, interval)` returns 252 for stock and the 365-day basis for crypto, and `bars_per_day(asset_class, interval)` returns 1 / 24 / 288 for crypto 1d / 1h / 5m; a trade is counted as a bar where the weight vector changes; `summary` returns NaN Sharpe for a flat (std == 0) series; `cross_check_daily` flags a max absolute daily-return difference over 1%.
4. Runner decision rule, applied to SMA 5/20-days on BTC/USD (the only candidate in Approach A; other strategies join only after this rule has been applied once), Alpaca bars for all lanes, 2021-01-01 to now, at 25 bps per side with a 1-bar execution delay: build the always-on runner only if the 5m or 1h net Sharpe beats the 1d net Sharpe by at least 0.3 AND that winning lane's net Sharpe is above 0 AND above buy-and-hold Sharpe over the same window AND the winning (faster) lane has at least 100 trades (a trade is a bar where the weight vector changes; the 1d lane has no trade minimum). [CEO D10] The 0.3 margin is a judgment call, not a statistic; with three intervals, three costs and a window that is mostly one crypto regime, treat the result as evidence for one rule, not proof. Otherwise crypto runs on a scheduled hourly or daily job and no always-on runner is built.

## CEO amendments merged into the plan (SELECTIVE EXPANSION)

### X1 `--grid` specification
- `STRATEGIES` registry in `src/lab/strategies.py`: name -> (`strategy_fn`, requirements: columns needed, minimum symbols, allowed asset classes).
- `--grid` runs every registered strategy whose requirements the symbol set meets, and prints one row per strategy with the same summary columns. A strategy that cannot run is skipped with a one-line reason (for example "needs volume; crypto volume strategies are out of scope for A", "needs >= 2 symbols").
- Weight allocation across a symbol set: single-symbol signal strategies (SMA) apply their signal to each symbol independently with weight = signal x allocation x leverage / N, so a row sums to at most allocation x leverage; multi-asset strategies (dual momentum) allocate across the set themselves.
- Window parameters are expressed in days and converted to bars per interval (`bars_per_day(asset_class, interval)`, also in `src/lab/run.py`): SMA 5/20 days (D5) and dual-momentum lookbacks 63/126/189/252 days; the grid passes the interval, not window sizes. Lab defaults: allocation 1.0, leverage 1.0.
- Registry entries are strategy + parameter set, so dual momentum is four entries (lookbacks 63, 126, 189 and 252 days) and the grid prints one row per entry; the X2 `params` column holds that entry's parameters (for example `lookback_days=126`).
- Test: the grid prints exactly one row per compatible registry entry and skips an incompatible one with a reason.
